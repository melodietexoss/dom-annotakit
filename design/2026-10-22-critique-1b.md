## Area A — server mode: is "wrap createMiddleware on http.createServer" enough?

**Yes for the REST surface; no for live updates; configDir/port wiring is non-obvious.**

What the middleware actually needs (routes.ts:1433-1507):

- **URL prefix only.** `if (!urlStr.startsWith('/annotakit/')) { next?.(); return; }` — mounted
  at the origin root, no path stripping, `next` optional. Route table keys off
  `API_BASE = '/annotakit/api'` (routes.ts:36, events.ts:116).
- **Origin from the request:** `http://${req.headers.host ?? 'localhost:6006'}` (routes.ts:1440),
  and only a request that passes the access gate updates `rt.origin` (routes.ts:1496) — used for
  issue-body/export links.
- **Lazy bootstrap:** `handleApi` calls `bootstrap(configDir)` on the first API request
  (routes.ts:702) — no SB lifecycle required.
- **No SB/vite bits.** `import type { IncomingMessage, ServerResponse } from 'node:http'`
  (routes.ts:14). Grep of `src/server` for `storybook`: **zero imports** — hits are only comments
  and console strings (store.ts:2/721, env.ts:2/95, ghsync.ts:2/225, gh.ts:61-79, routes.ts:2/4/192,
  sync.ts:2/88/141-143, merge.ts:2, digest.ts:2). The claim "server has zero SB imports" is TRUE.
- **Access gate inherited cleanly:** loopback peers free; non-loopback need `ANNOTAKIT_API_KEY`
  + `x-annotakit-key` (routes.ts:309-339); CORS loopback-only (routes.ts:349-381). Same-origin
  host app + iframe need neither.

**P2-4 (finding): THREADS_CHANGED is channel-emitter-only; there is no dev-mode poll fallback.**
`broadcast()` is `emitToChannel?.(...)` in try/catch — "channel is best-effort live sync; REST is
the source of truth" (routes.ts:68-74); `serverChannelHook(channel)` merely stores the emitter
(routes.ts:1513-1521). Upstream SB calls it via `experimental_serverChannel` (preset.js:101-103).
The manager's live updates are `ch.on(THREADS_CHANGED, onChange)` and nothing else in dev mode
(manager/index.tsx:354-364); static mode uses storage events instead (366-380). **If the
standalone entry mounts only `createMiddleware`, `emitToChannel` stays null and every panel and
layer silently loses live updates** (the panel still refreshes on its own actions, but not on
agent replies / other-tab mutations). Amendment: `src/server/standalone.ts` must call
`serverChannelHook(emitter)` (or `setChannelEmitter`) with a host channel AND the host must
transport it to the browser (poll, SSE, or WS) into the same channel object the panel + layer
subscribe to. D3a/D2a never says this. Not a data-integrity hole — a parity hole.

**P2-8 (finding): configDir semantics are a trap.**
`projectRoot(configDir) = path.dirname(path.resolve(process.cwd(), configDir))` (env.ts:21-24) —
the root is the configDir's *parent*. `devServerHook` defaults configDir to
`process.env.STORYBOOK_CONFIG_DIR ?? '.storybook'` (routes.ts:1525-1528) — SB-specific env name and
dir name. Passing the repo ROOT as configDir makes projectRoot its parent (wrong store root, wrong
`.env` root, wrong git ops root). Amendment: standalone.ts passes an explicit subdirectory, e.g.
`<repoRoot>/.dom-annotakit`, and bootstraps with the real port via the devServerHook shape
(`bootstrap` is *not* exported; the port-correct path is `devServerHook(shimApp, {configDir, port})`
— shim `app.use` stores the middleware). Why port matters: boot origin defaults to
`http://localhost:6006` (routes.ts:220) and `ghsync.start()` runs at bootstrap (routes.ts:243) —
issues minted before the first authorized request would carry 6006 links (the v0.4.0 "6006-in-6007"
bug upstream already fixed once).

Also note for B: `.env` discovery candidates are `[projectRoot/.env, configDir/.env, cwd/.env]`
(env.ts:70-74) — **the cwd candidate can load a foreign project's .env** (see P1-1).
`kitRepo()` reads the *package.json next to the server bundle* (env.ts:397-419) — after vendoring it
reads dom-annotakit's own package.json, so the cross-repo-leak guard still functions (and its
warning text still says "storybook-annotakit repo ITSELF" — routes.ts:173, P3-9).

## Area B — store location: what is the "consumer project" in server mode?

D3a never says. Upstream: `storeLocation(configDir, {forceClassic})` →
`<git-common-dir>/annotakit/` (git mode) or `<configDir>/annotakit` (classic) (env.ts:369-375);
bootstrap decides by `config.autoSync !== false` (routes.ts:115-117). "Consumer project" is
defined by configDir/cwd — i.e. **wherever the server process is run from**. The autoSync walk-up
(git-common-dir of `projectRoot`) is sane ONLY if that root is a deliberate choice; captures can
live anywhere, and a cwd inside an unrelated git repo silently adopts that repo's git dir.

**P1-1 (finding — the most dangerous hole): same-repo dual-kit collision.**
The flagship deployment (GenEditor-ui: SB10 consumer of storybook-annotakit AND the source of the
SingleFile captures) makes it natural to run the dom server *from the captures repo*. If both kits
ever run against one git repo (dom server cwd/configDir in the same repo as the SB kit):

1. **One store:** both engines open the same `<git-common-dir>/annotakit/threads.db`
   (env.ts:373) — two server processes on one WAL db, threads from both review streams in one store.
2. **One orphan branch:** both push `refs/heads/annotakit` (fallback `annotakit-store`)
   (sync.ts:106-107) with the same adoption marker `'annotakit-store: v1'` (sync.ts:84) — each
   engine's always-merge union adopts the other's snapshots as its own store.
3. **Cross-stream mirroring:** ghsync backfill mints issues for **every unmapped thread in the
   store** — the SB engine would mirror dom-kit capture threads (labeled `annotakit`) and
   vice-versa. The default-label change separates *pull filters* (Area C) but does nothing here,
   because the contamination happens before labels are chosen per-engine: both engines read the
   same rows.
4. **Env bleed:** `ANNOTAKIT_GH_REPO/_LABELS/_TOKEN` are process-global names, and the cwd
   `.env` candidate (env.ts:73) can hand the dom server the SB kit's repo+labels wholesale.

Amendments (pick both):
- **Isolate paths (recommended, surgical, COPY-MAP'd):** EDIT `env.ts` `storeLocation` →
  `<git-common-dir>/annotakit-dom/` and `sync.ts` `BRANCH_PRIMARY` → `'annotakit-dom'`
  (fallback `annotakit-dom-store`). The shared README marker line can stay (same vendor lineage,
  well-defined adoption). List both as EDITs; D3a's "copied unchanged" sentence becomes false in
  exactly these two lines — better honest than silent.
- **Pin .env discovery in standalone.ts:** always pass an absolute configDir inside the tool repo
  and document "run the server from the dom-annotakit repo"; optionally EDIT env.ts to drop the
  bare-cwd `.env` candidate for the standalone entry.

**Honest default for B (proposed):** the *consumer project is the dom-annotakit repo itself* (D1b
makes it a git repo with GH/GL remotes). Store at that repo's
`<git-common-dir>/annotakit[-dom]/threads.db`; autoSync durability pushes the orphan branch to the
tool repo's remote for free; the captures directory is *data* (referenced by the manifest), never
the store owner. State this in D3a. For a "review corpus in the consumer repo" mode, document it as
the dual-kit case and require the isolation above.

Bake parity: the bake's store ladder `--store → $ANNOTAKIT_STORE_PATH → git-common-dir(cwd) →
configDir/annotakit` (bake:341-350) has the same cwd-git-discovery property — see P2-6.

## Area C — default label `dom-annotakit`: really one line in env.ts?

**No. env.ts contains no label default at all.** `ghLabelsEnv()` returns null when unset
(env.ts:223-228). The default `annotakit` is hardcoded in **five** places:

| site | evidence |
|---|---|
| server default + `/health` `githubLabel` field | routes.ts:45 `const GH_LABEL = 'annotakit';` → `resolveGhLabels` fallback (routes.ts:55) and `githubLabel: GH_LABEL` in health (routes.ts:775) |
| ghsync engine fallback | ghsync.ts:121 `const labelsOf = opts.labels ?? (() => ['annotakit']);` (unreachable via routes, but vendored) |
| static client default | ghClient.ts:54 `const DEFAULT_LABEL = 'annotakit';` → `resolveGhConfig` (ghClient.ts:587) |
| bake default | bake-static-threads.mjs:327 `labels: labelList.length ? labelList : ['annotakit']` |
| heal-mirrors default | heal-mirrors.mjs:66 `const labels = (arg('labels') ?? 'annotakit')...` |

Amendment: D3b/COPY-MAP must list all five edits (routes.ts + ghClient.ts + bake + heal-mirrors +
ghsync fallback), and the COPY-MAP `env.ts` EDIT row as written is simply wrong — env.ts needs no
label edit; what it *may* need is the store-path/.env amendments from P1-1.

**Stream separation verified:** the pull filter AND-combines — server
`/repos/{r}/issues?labels=${labels.join(',')}` (gh.ts:307-310); client same with the last-wins
hazard pinned (ghClient.ts:403-412). With distinct defaults the two kits' issue sets are disjoint
in one repo; each engine pulls only its own label set. (`SKILL.md` §3's health example
`"githubLabel": "annotakit"` and Path A "list issues labeled annotakit" become the *tool's own*
runbook's job to update — new repo, new docs.)

**Sentinel & footers (checked):** `GH_SENTINEL = '<!-- annotakit -->'` (gh.ts:18, duplicated
ghClient.ts:65) is an engine-identity marker, not label-scoped — **leave unchanged** (pull filters
by label first; system-notice suppression depends on the prefix match, ghsync.ts:788,
ghClient.ts:1645). The `- thread id:` metaline stays (the adoption anchor — SKILL §4). Hardcoded
`'annotakit'` *author* names on system comments (ghClient.ts:1369/1587) are fine.

**Env-sharing caveat (P3):** `ANNOTAKIT_*` are process-global; a shared `.env` at a common root
would configure BOTH kits identically (same repo AND labels) — the separation then silently
collapses. Document: per-kit config lives in each kit's own `<configDir>/annotakit.config.json`
(config file beats env, routes.ts:51-56,135) or in each process's own environment.

## Area D — static-mode bake + staticStore scope

Verified sound:

- **Marker/seed consumed unchanged:** bake writes `{threads, deleted}` (bake:470 — "static-mode
  marker + seed", always written even empty, zombie rows suppressed, tombstones carried);
  staticStore's `SeedDoc` reads exactly `{threads, deleted}` with per-entry validation
  (staticStore.ts:96-100, 121-153). `annotakit-gh.json` `{token, repo, labels, pollMs}` only when
  token+repo (bake:479-490) — probeBakedGhConfig/resolveGhConfig consume it unchanged. The
  dom-annotakit-manifest.json addition is purely additive — nothing upstream reads it. ✓
- **Scope derivation:** `staticScope()` = origin + directory of the **parent** (manager/host)
  URL (staticStore.ts:72-86) — the capture iframe's layer anchors on the host app, so panel (host
  at `/`) and layer (iframe at `/captures/x.html`) resolve the SAME scope `http://host/`. No
  storyId in any storage key. Seed fetch path: candidate 1 = own doc dir (`/captures/…` → instant
  404), candidate 2 = parent dir (`/annotakit-threads.json` next to host index.html) → hit,
  candidate 3 = origin root (staticStore.ts:124-131). Health ladder likewise: baseURI-relative
  then origin-root (mode.ts:38-47). So app-at-`/` + captures-at-`/captures/` works unchanged,
  with one wasted 404 per iframe probe (harmless; document).
- **No SB-bake collision:** scope is per origin+directory (D3b's claim holds); an SB bake on the
  same origin under a different directory gets a different scope key.

**P2-6 (finding): the bake's cwd-git-discovery + `--base` are SB-shaped.**
For a captures-directory bake run, the ladder's `git rev-parse --git-common-dir` **from cwd**
(bake:343-348) can silently read an unrelated repo's store (or the SB kit's, per P1-1) — the bake
should REQUIRE `--store` (or default it to the tool-repo store documented in B) and the EDIT row
must say so. `--base` (bake:386-441) assumes a Storybook index.html ("not a storybook build
output?", the iframe.html exception, SB ref-shape commentary) — the dom host is a Vite app whose
default build emits **root-absolute** `/assets/...` refs, which the ref-shape gate treats as
"absolute but not under base" only when outside; the clean amendment is to build the host with
`base: './'` (or the real subpath) in Vite config and not rely on `--base` injection at all. Bake
default label + `--selftest` behavior stay (P2-3 covers the label).

## The single most dangerous hole

**P1-1:** run the dom server against a capture corpus that lives in a repo which also runs the SB
kit (the GenEditor-ui flagship case), and both engines open the *same* threads.db, push the *same*
`refs/heads/annotakit` orphan branch, and backfill-mirror *each other's* threads under both labels
— silent cross-stream data contamination that the default-label change (D3b) does not touch,
because the two stores were never supposed to be one. Fix is two surgical lines
(`annotakit-dom` store dir + branch) + a pinned configDir/.env rule; without it, the first real
deployment can corrupt two review streams at once.

## Bottom line

D3's architecture (two modes, wholesale engine copy, parity semantics) is sound and unusually
well-supported by upstream code; but the COPY-MAP has two verdicts that are wrong as written
(events.ts REPLACE, legacyMirror.ts SKIP), one factually false claim (the one-line env.ts label),
and D3a is silent on the two things that actually bite at runtime: where the store lives, and how
THREADS_CHANGED reaches the browser without SB's server channel. Approve D3 with amendments;
re-issue COPY-MAP rows for events.ts, legacyMirror.ts, env.ts, routes.ts, ghsync.ts, ghClient.ts,
digest.ts, manager, bake, heal-mirrors per the table above.
