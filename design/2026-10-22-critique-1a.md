## D1a — iframe + injected layer vs reverse-to-TSX — APPROVE

The fidelity/cost argument holds and is *stronger than the doc states*:
captures carry full inline CSS (`:root{--sf-img-6: url("data:…")}`),
Shadow-DOM-serialized web components, and 300KB–66MB bodies — a reverse-to-TSX
pipeline would be a lossy simulation per capture, and the pin engine already
proves itself on frozen, fiber-less DOM (upstream `transient:true` pins).
Verified the engine's DOM purity: `anchor.ts` (sole dep `@medv/finder`,
global-`document` helpers only), `hittest.ts` (injectable deps), `cascade.ts`,
`describe.ts`, `styles.ts` — all iframe-safe.

Missed failure modes (all P2/P3 — none reverses the decision):

- **[P3-14] Fidelity is high but not total — document the residual.** Magnific
  captures reference sprite icons by root-relative `xlink:href=/svg-sprite/sprite/<hash>.svg#search`
  → those `<use>` icons 404 on our origin (invisible icon slots). 1–2 external
  `<link>`s and HFAssetLib's 3 external `<img>`s mean review-time network
  calls (the "renders from disk" claim is ~99% true, not 100%). Nested
  iframes exist in the corpus (hidden, `src`-less Usersnap frame in
  `magnific-reference-general-annotated.html`) — `elementsFromPoint` cannot
  cross frame boundaries, so content inside captured frames is unpinnable.
  EVIDENCE: `grep '<use xlink' magnific-*.html`; iframe tag `<iframe name=us-entrypoint-globalSetup … style="display: none…">`.
  AMENDMENT: add a "known fidelity limits" note to D1a (sprite/external
  assets render broken-as-captured; nested-frame content unpinnable) so
  reviewers don't file phantom bugs.
- **[P3-19] `rel=expect blocking=render` is present in magnific captures**
  (`<link rel=expect blocking=render href=https://www.magnific.com/…#app-ready>`).
  Parser completion unblocks it, so the `load` event is unaffected, but first
  paint inside the iframe may be delayed. AMENDMENT: verify in the E2E smoke
  that the capture paints promptly; nothing else needed.

## D2a — same-origin iframe + layer injection — APPROVE-WITH-AMENDMENTS

What held up under adversarial checking (credit where due):

- **Module-scope safety of the layer bundle is exactly as COPY-MAP claims.**
  Grepped every module-level statement in `layer.tsx`: the ONLY SB couplings
  are `import { addons } from 'storybook/preview-api'` (L19), `sbChannel()`
  (L74), `storyRoot()` (L97), `buildStoryRef` (L23/L1412),
  `inspectComponent/correctSource` (fiber) — precisely the five substitution
  points listed. All `window.*` usage is timers/listeners/innerWidth/Height —
  iframe-correct.
- **Static-mode scoping survives the port unchanged** — a genuine surprise
  win: `staticStore.ts` `staticScope()` (L72–86) anchors on
  `window.parent.location.href` and `probeSeed()` (L124–131) has a
  parent-directory candidate in its ladder — upstream already runs the store
  inside a preview iframe. In our shape parent = host app → correct scope and
  seed discovery. The COPY-MAP "scope doc" edit may be a no-op; verify, and
  if so delete the edit line.

Findings:

1. **[P2-7] The iframe scrolling contract is unspecified — and it is the
   load-bearing layout decision.** Pins are `position: fixed`
   (`styles.ts` L40; `.annota-root` L8–11 `position: fixed; inset: 0`) —
   fixed to the IFRAME'S viewport box, which is exactly right ONLY if the
   iframe is host-viewport-sized and scrolls INTERNALLY (the SB-preview
   shape the layer was hardened in). If the host instead sizes the iframe to
   full capture height and lets the host page scroll, pins stay glued to the
   iframe's top-left box while content scrolls past — every pin visibly
   detaches. D2a says "the iframe sits at the host's content width" and
   nothing about height/scroll. AMENDMENT: pin the contract in D2a: iframe
   fills the host's visible area (100% height, host never scrolls; capture
   scrolls inside the iframe), and add an E2E assertion (scroll the iframe,
   pins must stay viewport-fixed).
2. **[P2-8] No navigation guard — a link click destroys the session.**
   The corpus keeps original hrefs: the fixture capture alone has 7
   `<a href=https://www.magnific.com/app…>` (and dead form actions). A
   reviewer clicking any link navigates the iframe to the live site: the
   layer, pins, and notes vanish; the host's `contentWindow` calls now hit a
   foreign (possibly cross-origin) document. "Try/catch'd already" is a
   crash guard, not an answer. AMENDMENT: on injection, add a capture-phase
   `click`/`submit` interceptor on `contentDocument`
   (`preventDefault` for `a[href]` and form submits, allow modifiers /
   `target=_blank` per taste), plus a load-guard: if `iframe` `load` fires
   with `contentWindow.location` ≠ capture URL, show an "away from capture —
   reload" notice and skip injection. ~15 lines of host code, zero upstream
   edits.
3. **[P2-6] z-war: pre-import note cards paint ABOVE the annotakit surface.**
   The SingleFile card style is `.note { position: absolute; … z-index:
   2147483646 }` (grep of the capture's shadow `<style>`), while
   `.annota-root` is `z-index: 2147483000` (`styles.ts` L11). Cards can sit
   over pins AND the composer/thread cards (z 20/30 inside .annota-root's
   2147483000 context loses to any root-context 2147483646), intercepting
   clicks — the "zero surprise" pre-import render is surprising exactly when
   you try to work. AMENDMENT: one-line COPY-MAP'd edit in `styles.ts`:
   `.annota-root { z-index: 2147483647 }` (and the frozen veil 2147482000 →
   2147483646), with a comment referencing this audit. Keep cards visible
   underneath; review wins the z-war by design.
4. **[P2-9] `mode.ts` health ladder loses its subpath candidate in our
   shape.** `healthOk()` candidates are `new URL('annotakit/api/health',
   document.baseURI)` (= the CAPTURE's directory inside our iframe —
   structurally useless here, guaranteed 404) and origin-root. Root-served
   server mode works; but a server (or proxy) deployment under a subpath
   fails BOTH → `probeMode` falls to `probeSeed` → no seed in server mode →
   `'down'` → the layer honestly refuses to write. Server mode silently
   degrades to read-only under any subpath, and nothing in the design
   notices. (Static mode is safe: `probeSeed`'s parent-aware ladder finds
   the bake next to the host app.) AMENDMENT: the host injects a build/bake
   constant (host app base URL) with the layer bundle; add it as the FIRST
   health candidate — one surgical `mode.ts` edit, COPY-MAP'd. Alternative
   (weaker): document origin-root as a hard requirement of server mode.
5. **[P2-12] Freeze mode on huge captures = full-DOM clone.**
   `captureFrozenView` builds a body-level container holding a
   `storyClone` of the WHOLE root (`snapshot.ts` FrozenMount contract) — on
   the 66MB `magnific-reference-character-selector.html` that's potentially
   a ~1M-node clone: seconds of jank or tab OOM. The toolbar plan keeps
   freeze; the risk table only guards LOADING. AMENDMENT: manifest already
   carries file size — host disables the freeze button above a threshold
   (e.g. 20MB, matching the existing warn line) with a hint; zero upstream
   edits. (Recall is already de-scoped to focus-pin per D3d — good.)
6. **[P3-13] Pin the layer script's module type in the design.** tsup's
   browser config is `format: ['esm']` (upstream tsup.config.ts), so
   `dist/layer.mjs` carries `export`/module syntax — the host MUST append
   `<script type="module" src="/layer.mjs">`. A classic `<script src>` is a
   guaranteed SyntaxError and this is exactly the detail that gets lost
   between design and implementation. AMENDMENT: write the tag, verbatim,
   into D2a.
7. **[P3-18] CSP metas: absent in the current corpus (verified 30 files) —
   keep it that way, explicitly.** If a future capture retains a strict
   `Content-Security-Policy` meta, both the layer script fetch AND the
   overlay's runtime `<style>`/inline-style usage can be blocked inside the
   iframe, and the file-URL serving model gives no pre-load hook to strip it.
   AMENDMENT: add to the risk table: "if a capture with CSP-meta appears,
   the server's static handler gains a streaming meta-strip for captures"
   — planned, not built (corpus says defer).

## D2b — `anchor.ts` unchanged; captureId — APPROVE-WITH-AMENDMENTS

What adversarial checking CONFIRMED (the "unchanged" claim is well-founded):

- SingleFile's unquoted-attribute serialization (`<div data-note-id=3 …>`)
  is invisible to the engine — parsing normalizes it; `querySelector` /
  `getAttribute` / finder all operate on the parsed DOM.
- `data-single-file-*` additions don't enter identity: FINGERPRINT_ATTRS
  (`anchor.ts` L18–27) is aria-label/title/placeholder/alt/name/type/href/
  data-testid; `data:` URIs live in `src`/`srcset`, which are NOT
  fingerprinted. `href` is kept LIVE by SingleFile (original site URLs —
  verified 7 real hrefs) → stable, even useful identity.
- Note cards cannot pollute anchors even unstripped: `isSkippable`
  (L66–73) rejects TEMPLATE subtrees, `collectTextNodes` never enters shadow
  roots, the note element's light-DOM `textContent` is empty (all card
  content is inside the declarative-shadow template), and the card is
  `position: absolute` → zero layout impact on targets' bboxes.
- Corpus edge confirmed REAL for css stability: `cssPath` → `@medv/finder`
  emits `:nth-child` paths (tag/class/nth-child strategy), so element
  ADD/REMOVE among target siblings shifts later siblings' indexes. This is
  the mechanical basis of finding 12 (strip ordering) below, and is honest
  degrade via the text/attr rungs otherwise.

Findings:

8. **[P2-10] `captureId` = basename: three unhandled identity cases.**
   (a) Collision: the tool serves a "captures directory" generally; two files
   with the same basename in different subdirectories produce the same
   `captureId` → threads merge across different captures. The current corpus
   is flat (30 files at repo root) — luck, not design. (b) Rename = silent
   identity change: threads stay keyed to the old id and disappear from the
   new capture's list with no explanation. (c) The design ignores the richer
   identity data SingleFile embeds IN THE FILE: every sampled capture opens
   with `<!--\n Page saved with SingleFile \n url: https://www.magnific.com/app/projects/all-assets\n saved date: Tue Oct 13 2026 23:07:58 GMT-0700 …\n-->`
   (immediately after `<html …>`). AMENDMENT: keep filename-as-id (it IS
   stable and semantic) but (1) manifest builder derives id from the
   RELATIVE PATH (sanitized) or fails LOUDLY on basename collision;
   (2) manifest records the embedded `url` + `saved date` per capture
   (provenance, and free re-save detection: same url + different filename →
   surface a hint, PLAN the thread-migration offer); (3) document "rename =
   new capture identity" in the README/risk table.
9. **[P3-16] `single-file-highlight-*` classes can leak into css
   selectors.** A user highlight adds classes to arbitrary elements; the
   finder className filter (`name.length > 3 && !name.startsWith('_') &&
   !/(?:^|[-_])(?:css|scss|module)/` — `anchor.ts` L116) happily admits
   `single-file-highlight-yellow` → a captured selector can embed it →
   re-save without the highlight breaks the css rung (honest ladder degrade,
   but avoidable). AMENDMENT: D2b's own escape hatch applies — one scoped,
   tested tweak: add `/^single-file-/` to the className exclusion, COPY-MAP'd.
   (Do NOT touch FINGERPRINT_ATTRS — no evidence of need.)

## D2c — SingleFile import — APPROVE-WITH-AMENDMENTS (1–3 BLOCKING)

Format facts re-verified on the real fixture
(`magnific-folder-new-asset-flow-annotated.html`): 4 `<single-file-note
data-note-id=N data-note-offset-x=X …>` elements; each wraps
`<template shadowrootmode=open>` with the sticky card; targets carry
`data-single-file-note-refs=N` in LIGHT DOM; **tree-parse shows each note
element sits as a SIBLING immediately after its target** (same parent, next
position — notes 1–4 at depths 37–48 alongside targets at matching depths),
NOT inside the target subtree, NOT body-appended. Note text carries newlines
and entities (`"The best way…flows: \n- 'Create' -&gt; which goes…"`),
validating DOM-parse-over-regex (the python extractor's `unescape` +
`re.S` fallbacks exist precisely because regex fights this).

BLOCKING findings:

1. **[P1] Live-DOM note content is in `el.shadowRoot`; `template.content`
   is EMPTY there — the design's read path is wrong, and Node tests will
   mask it.** `template shadowrootmode=open` is declarative Shadow DOM: on
   live parse, the browser creates the shadow root on the note element and
   the template's children are adopted INTO it — the `<template>` marker
   remains with an EMPTY `.content`. So in the live iframe:
   `note.shadowRoot.querySelector('textarea')` works;
   `note.querySelector('template').content` finds NOTHING. Inverse in
   tests: neither jsdom nor Node DOMParser implements declarative shadow
   attach — there `template.content` holds the card and `shadowRoot` is
   null. Result if the spec says "shadow template content" and the
   implementer writes the obvious `template.content` read: the manifest
   (Node-side) counts N notes → "Import N notes" affordance appears → the
   live import parses 0 notes → silent no-op, with every unit test green.
   EVIDENCE: capture bytes above; declarative-shadow parse semantics; jsdom
   non-support. AMENDMENT (must go into the design text): the reader is
   `contentOf(note) = note.shadowRoot ?? note.querySelector('template')
   ?.content ?? null`, and the test matrix pins BOTH shapes (a live-DOM
   browser E2E on the real capture — the design's own agent-browser
   discipline — plus the Node fixture).
2. **[P1] The idempotency marker has NO type home — D2c contradicts D2b's
   and COPY-MAP's "zero type changes".** The design says imported threads
   carry `target.context.singleFileNoteRef = N` + `source:'singlefile'`.
   Vendored `TargetContext` (`shared/types.ts` L154–179) has no such field;
   `Comment.source` is `'local' | 'github'` (L233). COPY-MAP pins
   `types.ts` AS-IS ("storyId carries captureId — zero type changes") and
   D2b reiterates it. As written: compile error, or an untyped cast that
   review round 2 will flag as a vendoring-rule violation. The
   "markers survive merges" CLAIM itself verified TRUE — merge is
   spread-based (`merge.ts` L36 `{…t, comments: …}`, L129/L144 comment
   clones), PATCH_MERGEABLE_FIELDS includes `target` (`routes.ts` L595),
   `validateTargetShape` requires only `context.tag` (L541–543, no field
   whitelist), store spreads whole threads (`store.ts` L270/L588) — extra
   context fields ride through opaquely. AMENDMENT: (a) make idempotency
   structural, not marker-based: deterministic thread id
   `singlefile-<captureId>-<note N>-<textHash8>` using `ThreadInput.id` +
   the server's existing POST replay door (`routes.ts` L1178
   `{…thread, replayed:true}`) — re-import is then idempotent at the store
   doors with ZERO type changes; (b) for provenance/display, make ONE
   additive types.ts EDIT (extend `Comment.source` with `'singlefile'`;
   add optional `TargetContext.singleFileNoteRef?: string`) and list it in
   COPY-MAP — a 2-line, additive, merge-safe edit. Stop pretending it's zero.
3. **[P1] Dangling-ref "honest orphan" is unconstructible as specified —
   naive implementation fabricates evidence.** `ThreadTarget` REQUIRES
   `context.tag` and `bbox` (`types.ts` L214–221); orphan pins render at the
   stored fragment ("pin renders at stored fragment bbox"). For a dangling
   note the target NEVER EXISTED in this DOM: there is no tag, no bbox, no
   fragment — only the note text (and the note's own sticky coords). The
   design hand-waves "honest orphan pin with the note text preserved" — the
   obvious implementation (fabricate `{tag:'unknown', bbox:{0,0,0,0}}`)
   stacks every dangling pin at the capture's top-left corner masquerading as
   positional evidence — a direct violation of the "evidence kept" honesty
   contract. This is MAINLINE, not edge: the corpus's own analysis records 6
   `<element not found for note N>` across files
   (`docs/analysis/annotations.txt` L18, L26, L110, L114, L118, L138).
   AMENDMENT: define the import-orphan shape explicitly: kind `'pin'`,
   `selector.fragment` = the note's own `data-note-offset-x/y` (which D2c
   already stores for provenance) clamped into the root, `context.tag =
   'single-file-note'`, the `singleFileNoteRef` marker + a status-line /
   pin-subtitle "dangling SingleFile note — target not in capture" so the
   fabricated position is LABELED as card-relative, not evidence; OR (simpler,
   defensible) dangling imports render NO pin and appear panel-only with the
   dangling badge. Pick one in the design and pin it with a fixture test
   (the design already lists a dangling-ref case — good).

Non-blocking findings:

11. **[P2-11] Root-level targets are real and unhandled.** The corpus has
   notes ON the `<html>` element: `TARGET: <html lang=en … data-single-file-note-refs=5>`
   (annotations.txt L34) and a whole capture's notes on one root:
   `<html lang=en class=dark dir=ltr style data-single-file-note-refs="1 2 3 4">`
   (L106). The import path bypasses `isPinnableTarget` (which enforces
   `target !== scopeEl && scopeEl.contains(target)`, `hittest.ts` L165), so
   `captureAnchor(<html>, root)` runs degenerately: finder fails (el is not a
   descendant of root), bbox goes negative-root-relative, first-text-node
   quote is page noise. AMENDMENT: importer special-cases targets that ARE
   (or contain) the anchor root / html / body → import as a PAGE-LEVEL note
   (region over the capture viewport, or orphan-with-context per finding 3),
   never through the plain element path.
12. **[P2-15] Strip/capture ordering must be pinned: strip FIRST.** Notes
   are layout-inert (absolute-positioned shadow card, empty light text) so
   bboxes/text are identical either way — but they are ELEMENT SIBLINGS, and
   finder emits `:nth-child` selectors: capturing an anchor while cards are
   present then stripping shifts nth-child for later same-parent siblings →
   css rung breaks on next-session resolve (falls to text rung — approx
   instead of resolved). AMENDMENT: mandate the invariant in D2c: "card strip
   (auto or import-time) happens BEFORE any anchor capture on that capture,
   in every session" — one sentence, zero code. (Pre-import pins that later
   get a strip under them keep honest ladder degrade; note it.)
13. **[P2-4] Note-ids recycle across saves — the dedupe key silently eats
   NEW notes.** `data-note-id` is per-save sequential from 1 (fixture: 1–4;
   second capture: 1–3). Overwriting a capture file (same filename → same
   captureId) with a fresh save resets ids → naive dedupe on
   (captureId + noteRef) treats every NEW note as already-imported and skips
   it — silent data loss of exactly the annotations the user just made on
   the updated capture. EVIDENCE: id sequences restart at 1 in both real
   annotated captures; SingleFile's `saved date` header changes on re-save.
   AMENDMENT: fold the note TEXT into the identity — deterministic id
   `singlefile-<captureId>-<noteId>-<sha1(noteText)[0:8]>` (subsumes
   finding 2's fix): unchanged note → replay/no-op; edited/new note → new
   thread (old one degrades honestly if its target moved).
14. **[P2-5] Auto-strip keyed on "threads with the source" resurrects cards
   when the import is fully deleted.** User imports, deletes all imported
   threads (tombstones) → marker gone → next load re-renders the sticky cards
   over a review surface whose threads say otherwise. AMENDMENT: key
   auto-strip on an import-time per-capture flag the host owns (e.g.
   `localStorage['dom-annotakit:stripped:<captureId>']` or a manifest sidecar),
   OR check tombstones too (staticStore exposes deleted; server envelope
   carries them) — one decision, written down.
15. **[P3-20] Multi-note-single-target is real** (`refs="1 2 3 4"` on one
   element, annotations.txt L106): importer must iterate the SPACE-SEPARATED
   list per element (one thread per note), not one-target-one-note; cascade
   already fans the pins. Nested note-inside-another-note's-card is
   structurally IMPOSSIBLE (cards are shadow content; targets are light-DOM
   page elements) — close that design question with this evidence.
16. **[P3-21] Author default.** `singlefile-import` as default author is
   fine, but the design should state it rides `COMMENT_ORDER_KEY`-style
   settings precedence: settings override → else `singlefile-import`.
   (Minor; prevents a "who is singlefile-import" settings-UX question later.)

## What was adversarially checked and PASSED (keep as-is)

- `anchor.ts` byte-identical viability on SingleFile DOM (findings above are
  edits OUTSIDE anchor.ts, scoped and COPY-MAP'd — D2b's own escape hatch).
- DOM-parse-not-regex for notes (newline/entity evidence above).
- "The capture file is NEVER modified" — in-memory strip is safe and
  reachable (light-DOM elements).
- Highlights staying rendered / not converted (v0.1 scope) — no objection.
- The corpus's script/CSP/base cleanliness validating D2a's preconditions
  TODAY (findings 7 and P3-19 add the forward-looking guardrails).
- `captureViewportWidth` degrade story (`anchor.ts` L316–318, ±2px) — sound
  in the host-controlled iframe width; resize = relayout mode by design.

## Priority roll-up

- **P1 (blocking):** (1) shadowRoot vs template.content read path;
  (2) idempotency marker's missing type home + zero-type-changes
  contradiction; (3) dangling-ref ThreadTarget fabrication.
- **P2:** (4) note-id recycling vs dedupe key; (5) root-level `<html>`
  targets; (6) z-war vs note cards; (7) iframe scrolling contract;
  (8) navigation guard; (9) subpath health ladder; (10) captureId
  collision/rename/embedded-metadata; (11) auto-strip vs deleted threads;
  (12) freeze on huge captures.
- **P3:** module-type pinning; fidelity-limits doc; strip-first invariant
  wording; highlight-class exclusion; drift-check script; CSP forward note;
  rel=expect paint check; multi-ref iteration; author default.

**Single most dangerous hole:** finding 1 — the declarative-shadow read
path. It kills the entire import feature SILENTLY in the browser while every
Node-side test stays green (jsdom never attaches the shadow root), and the
design's own test plan (vendored-fixture unit tests) is built on exactly the
environment that masks it.
